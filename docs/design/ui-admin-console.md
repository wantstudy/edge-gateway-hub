# 管理后台界面设计（厂商侧 admin-console）

> 使用者：厂商运营/售后/客服（内部人员）。**与网关侧 `web-console` 代码、构建、部署完全分离。**
> 后台是「一机一码 + 激活码生命周期 + 换机重发」的**唯一执行侧**：发码、绑定、废弃、重发只能在这里做。
> 配套：`ui-design-system.md`、`ui-admin-console.md`（本文）、`prototype/iot-daq-ui-prototype.html`

---

## 1. 设计目标

1. **安全第一**：所有破坏性操作（废弃、重发、密钥退役）都是**高影响 + 低频率**，必须防误操作（二次确认 + 原因必填 + 对象名二次输入）。
2. **可溯源**：任意一台设备、任意一个激活码，都要能一键回答「它是谁、什么时候发的、绑到哪台机器、谁操作的、为什么废弃」。
3. **运营效率**：客服每天处理的是「客户换机了」「客户机器重装了」——换机重发必须能在 **3 次点击内完成**。
4. **异常可见**：B 档（默认）下厂商收不到业务数据，唯一的外部证据是**审计回执**。回执缺失/跳空必须显著可见，不能藏在二级页面。

**发放激活码（弹窗）**：租户[必选 ▾] · tier[专业版/免费版] · 有效期[12 个月/自定义] · 数量[1] · 预绑定机器码（可选，粘贴后显示指纹校验结果） · 备注 → 生成后支持**一次复制全部**（码不二次展示明文，仅可在详情页按权限查看）。

**废弃（`DangerConfirmModal`，本系统最危险操作）**

```
废弃激活码 IOT-2026-8C3F-…-A1
影响提示：
  · 该码绑定设备「6f2a…c1（华中智造 / 线1-网关-01）」将在下次心跳（≤24h）后
    **立即停止北向转发**，本地采集继续。
  · 客户侧会显示授权停用提示，需重新发放新码才能恢复。
  · 本操作不可撤销。
废弃原因（必填）  [ 客户更换硬件 / 设备报废 / 合同终止 / 误发放 / 其他 ▾ ]
补充说明          [ 文本域，必填 ≥10 字 ]
风险二次确认      请输入激活码后 8 位以确认：[ ________ ]
                                                  [取消]  [确认废弃]
```

**重发（弹窗）**

```
重发激活码（源：IOT-2025-1D90-…-3K，已废弃）
新机器码  ( ) 预绑定新机器码  [ C1D2-4E5F-…-9A0B ]（粘贴后校验格式与是否已被占用）
          ( • ) 留待首次激活时绑定（推荐，客户自助激活）
继承属性  tier 专业版（可覆盖 ▾） · 有效期 顺延 12 个月（可选：沿用源码到期日）
备注      [ 客户主板损坏，已寄修 ]
                                      [取消]  [确认重发]
→ 生成新码并建立 溯源链：源码 ← 重发于 ← 新码（详情页时间线可见）
```

要点：**废弃必须立刻生效**（不只是标记）；重发**不自动解绑**原设备（原设备已随废弃失效），两端都写进验收。

### 3.4 设备管理 `/devices` + 详情

列表列：机器码摘要 · 租户 · 设备名 · tier · 部署形态（native/docker）· 档位（A/B/C）· 授权状态 · 最近心跳 · 回执健康 · 首次激活时间。

设备详情重点：
- **心跳时序图**（近 7 天，缺失点标红）；
- **回执连续性**（B 档核心证据）：近 24h 的序号区间覆盖图，跳空区间标红并可下钻到区间号；
- 关联激活码与溯源链；
- **换机记录**；操作：`废弃关联激活码`（同 §3.2 危险确认）、`标记设备异常`（仅备注，不改授权）。

### 3.6 租户与策略 `/tenants`

租户列表 + 详情策略：tier 默认值、**校验档位 A/B/C（默认 B）**、设备配额、试用策略（3 天）、心跳间隔（24h）、离线宽限（7 天）、回执要求（是否强制）、联系人。修改档位属高影响操作，需二次确认并记审计。

要点：kid 轮换必须保证**旧客户端仍能验签**（客户端内置公钥集而非单钥），否则一次轮换等于全网设备失联——这是 task 45 的硬约束，界面必须把风险讲明。

## 4. 关键流程（端到端）

### 4.1 首次发码 → 绑定（正常销售）
后台发码（可选预绑定机器码）→ 客户在网关授权页输入码 → 云端校验未绑定/未废弃 → 绑定设备指纹 → 签发 Lease Token（含 tier + 档位）→ 详情页可见绑定记录。

### 4.2 换机重发（核心业务，目标 ≤3 次点击）
1. 客服在 `/transfers` 看到客户提交的换机申请（含原/新机器码与原因）；
2. 点「处理」→ 后台校验新机器码未被占用 → 一键执行「废弃旧码 + 重发新码」（同一事务，`reissued_from` 记录溯源）；
3. 系统展示新码（复制发给客户）→ 客户在新机激活。

### 4.3 误发放回收
未绑定的码 → 「作废」（不影响任何设备）；已绑定的码 → 只能「废弃」（会影响客户，需审批与原因）。

### 4.4 异常处置（B 档）
回执跳空告警 → 客服核实（联系客户确认是否检修/断电/更换设备）→ 若为硬件更换 → 走换机重发；若为软件问题 → 记备注并转技术支持。**不得仅凭跳空直接判定客户破解。**

## 5. 页面与接口对应

| 页面 | 依赖 API（task 45/46） |
|---|---|
| 总览 | `GET /admin/overview`、`GET /admin/receipts/summary` |
| 激活码管理 | `GET /admin/codes`、`POST /admin/codes/issue`、`POST /admin/codes/{id}/revoke`、`POST /admin/codes/{id}/reissue`、`GET /admin/codes/{id}` |
| 设备管理 | `GET /admin/devices`、`GET /admin/devices/{id}`、`GET /admin/devices/{id}/heartbeats`、`GET /admin/devices/{id}/receipts` |
| 租户与策略 | `GET/PUT /admin/tenants`、`PUT /admin/tenants/{id}/policy` |
| 回执与异常 | `GET /admin/receipts`、`GET /admin/receipts/anomalies` |
| 换机工单 | `GET /admin/transfers`、`POST /admin/transfers/{id}/process` |
| 密钥管理 | `GET /admin/keys`、`POST /admin/keys/rotate`、`POST /admin/keys/{kid}/retire` |
| 审计日志 | `GET /admin/audit` |
| 账号与角色 | `GET/POST/PUT /admin/users` |

**幂等要求**：`revoke` / `reissue` 必须幂等（重复提交同一请求不产生第二个结果），前端在提交期间禁用按钮并在超时后提供「查询上次结果」入口（而非直接重试）。

## 6. 验收要点

- [ ] 废弃操作：必须填原因（≥10 字）+ 输入激活码后 8 位二次校验，缺一项无法提交
- [ ] 废弃提示明确写出「原设备将立即停止北向转发，本地采集继续」
- [ ] 重发支持「预绑定新机器码」与「留待首次激活绑定」两种模式，并建立 `reissued_from` 溯源
- [ ] 换机工单处理支持「废弃 + 重发」合并执行，且整体 ≤3 次点击
- [ ] 激活码明文默认掩码，查看需权限且记审计
- [ ] 回执异常页含「异常 ≠ 破解」说明文案
- [ ] 密钥轮换界面明确提示「旧客户端仍可验签」与存量版本覆盖率
- [ ] 前端不持有签名私钥、不直连授权数据库；所有写操作走管理 API
- [ ] 构建产物独立于 `web-console`（不同的 Vite 工程与 dist）
- [ ] 后台域名/部署与网关侧隔离，且不暴露于公网明文（域名 + HTTPS + 后台自身鉴权 + IP 白名单可选）
